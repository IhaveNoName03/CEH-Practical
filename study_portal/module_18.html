Scenario & Objective

Scenario: The significant development of IoT is contributing to the proliferation of devices in daily life, from smart homes to automated healthcare. IoT devices lack basic security, making them prone to cyber-attacks. Hackers exploit IoT devices to gain unauthorized access to users' devices and data, build botnets for DDoS, spy on users, misuse sensitive information such as health records, install ransomware, monitor victims via CCTV, commit credit-card fraud, or gain access to homes. OT (Operational Technology) systems control physical processes (SCADA, PLCs, HMIs) and are often legacy, fragile, and safety-critical. As an ethical hacker and pen tester, you must have sound knowledge of hacking IoT and OT platforms using various tools and techniques; the labs provide real-time experience in footprinting and analyzing traffic between IoT/OT devices.

Objective: Perform IoT and OT platform hacking: (1) IoT/OT device footprinting; (2) capturing and analyzing traffic between IoT devices.

Overview of IoT and OT Hacking

Using the IoT/OT hacking methodology, an attacker acquires information via information gathering, attack surface area identification, and vulnerability scanning, then uses it to hack the target device and network. Phases: Information gathering; Vulnerability scanning; Launch attacks; Gain remote access; Maintain access. Many IoT devices (e.g., security cameras) host web interfaces over insecure HTTP instead of HTTPS and use default factory credentials, allowing interception of all traffic; attackers can use Wireshark to intercept traffic and decrypt Wi-Fi keys. Footprinting collects IP address, protocols (MQTT, ModBus, ZigBee, BLE, 5G, IPv6LoWPAN), open ports, device type, geolocation, manufacturing number, manufacturer, FCC ID, banners, certification.

Key Concepts
  • IoT (Internet of Things): Network of physical devices embedded with sensors/software that collect and exchange data over the Internet.
  • OT (Operational Technology): Hardware/software that monitors and controls physical processes, devices, and infrastructure (SCADA, ICS, PLCs, HMIs, RTUs).
  • IoT Architecture: Perception layer (sensors/actuators), network layer (gateways, protocols, connectivity), application layer (cloud, apps, data processing).
  • ICS (Industrial Control Systems): Umbrella term for control systems used in industrial production (SCADA, DCS, PLC-based systems).
  • SCADA (Supervisory Control and Data Acquisition): System that monitors and controls industrial processes across geographically distributed sites.
  • PLC (Programmable Logic Controller): Ruggedized industrial computer for automation of electromechanical processes.
  • RTU (Remote Terminal Unit): Microprocessor-controlled device interfacing objects in the physical world to a SCADA system.
  • HMI (Human-Machine Interface): Dashboard/operator screen for monitoring and controlling industrial processes.
  • DCS (Distributed Control System): Control system for a plant/process with distributed controllers.
  • MQTT (Message Queuing Telemetry Transport): Lightweight publish/subscribe messaging protocol for M2M/IoT; small code footprint, low bandwidth; broker + topics; QoS 0/1/2.
  • MQTT Broker: Central server that receives published messages and routes them to subscribers (e.g., Bevywise MQTTRoute).
  • MQTT Topics: UTF-8 hierarchical strings (forward slashes) used to route messages; e.g., High_Tempe.
  • MQTT QoS: 0 = at most once; 1 = at least once; 2 = exactly once.
  • MQTT Retain Flag: If 1, broker stores last message for future subscribers matching the topic.
  • DUP Flag: 0 = first attempt; 1 = possible retransmission of PUBLISH.
  • CoAP (Constrained Application Protocol): REST-like protocol for constrained devices; runs over UDP; DTLS for security.
  • Modbus: Industrial protocol; Modbus TCP on port 502; function codes read/write coils/registers; no built-in security.
  • DNP3 (Distributed Network Protocol 3): Protocol for utilities (power/water); TCP/UDP 20000; supports secure authentication.
  • OPC UA: Platform-independent industrial interoperability standard; port 4840.
  • BACnet: Building automation and control network protocol; UDP 47808.
  • Zigbee: Low-power wireless mesh (IEEE 802.15.4) at 2.4 GHz.
  • BLE (Bluetooth Low Energy): Short-range low-power wireless for IoT wearables/sensors.
  • 6LoWPAN: IPv6 over Low-Power Wireless Personal Area Networks.
  • Footprinting: Gathering IP, hostname, ISP, location, banners, device type, manufacturer, FCC ID, certification, protocols, open ports.
  • Shodan: Search engine for Internet-connected devices; filters by port, country, city, org, product, os.
  • Google Hacking (Dorking): Advanced search operators to find exposed sensitive IoT/SCADA resources (intitle:, inurl:, filetype:, site:).
  • Whois Lookup: Retrieves domain registration/contact info for protocol-standard organizations (e.g., oasis-open.org for MQTT).
  • IoT Attacks: Botnets (Mirai), DDoS, device hijacking, eavesdropping, firmware tampering, default credentials, insecure HTTP, MQTT topic injection/replay, unauthorized command injection.
  • OT Security: Network segmentation, air-gapping, ICS patching, monitoring, least privilege, physical security, anomaly detection.
  • MQTT Publish Message: Carries Topic Name, Message/Payload, Msg Len, Topic Length, Header Flags.
  • PUBREL (Publish Release): Response to PUBREC in QoS 2 flow.
  • PUBCOMP (Publish Complete): Response to PUBREL; completes QoS 2 exchange.
  • PUBREC (Publish Received): Acknowledgement of PUBLISH in QoS 2 flow.
  • PINGREQ/PINGRESP: Keep-alive messages between client and broker.
  • PUBACK: Acknowledgement for QoS 1 PUBLISH.
  • FCC ID: Device certification identifier searchable for manufacturer/regulatory info.

Key Protocols / Ports
  • MQTT (plain): TCP 1883 (default; defined by IANA as MQTT over TCP).
  • MQTT (TLS): TCP 8883 (MQTTS).
  • MQTT-SN: UDP 1883 (for sensor networks).
  • CoAP: UDP 5683 (plain), UDP 5684 (DTLS).
  • Modbus TCP: TCP 502.
  • DNP3: TCP/UDP 20000.
  • OPC UA: TCP 4840.
  • BACnet/IP: UDP 47808.
  • HTTP/HTTPS: TCP 80 / 443 (device web interfaces).
  • RTSP: TCP 554 (IP cameras/media).
  • SSH: TCP 22; Telnet: TCP 23; FTP: TCP 21.
  • SNMP: UDP 161/162.
  • AMQP: TCP 5671/5672; XMPP: TCP 5222.
  • KNX/IP: UDP 3671; EnOcean: sub-GHz.
  • Zigbee: IEEE 802.15.4, 2.4 GHz (channels 11-26).
  • BLE: 2.4 GHz ISM band.
  • LoRaWAN: 868/915 MHz ISM bands.
  • Bevywise MQTTRoute web UI: HTTP TCP 8080 (localhost).
  • Bevywise IoT Simulator web UI: HTTP TCP 9000 (localhost).

Defenses
  • Change default credentials on all IoT/OT devices; enforce strong, unique passwords.
  • Disable insecure services (Telnet, FTP, HTTP admin) and require HTTPS/SSH/TLS.
  • Segment OT networks from IT and the Internet; use firewalls, DMZ, and unidirectional gateways (data diodes).
  • Air-gap critical OT where feasible; monitor any bridging connections.
  • Encrypt IoT traffic (MQTTS 8883, CoAP DTLS 5684, TLS for HTTP) and authenticate clients/brokers.
  • Apply least privilege to MQTT topics and broker ACLs; disable anonymous access.
  • Patch firmware and OT software; maintain an asset inventory and vulnerability management.
  • Monitor network traffic with Wireshark/IDS for anomalous MQTT/Modbus/DNP3 commands.
  • Disable unnecessary ports and services; harden device configurations.
  • Use device certificates and mutual TLS for device identity.
  • Physical security for PLCs/HMIs/RTUs; restrict USB and console access.
  • Back up configurations and plan incident response for OT environments.
  • Register/track FCC IDs and vendor advisories; avoid exposing devices to Shodan (no public IPs).
