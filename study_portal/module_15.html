SQL Injection

SQL injection is the most common and devastating attack that attackers can use to take control of data-driven web applications and websites. It is a code injection technique that exploits a security vulnerability in a website or application's software. SQL injection attacks use a series of malicious SQL (Structured Query Language) queries or statements to directly manipulate any type of SQL database. Applications often use SQL statements to authenticate users, validate roles and access levels, store, obtain information for the application and user, and link to other data sources. SQL injection attacks work when applications do not properly validate input before passing it to a SQL statement.

Scenario: When attackers use tactics like SQL injection to compromise web applications and sites, the targeted organizations can incur huge losses in terms of money, reputation, and loss of data and functionality. As an ethical hacker or penetration tester (pen tester), you must possess sound knowledge of SQL injection techniques and be able to protect against them in diverse ways such as using prepared statements with bind parameters, whitelist input validation, and user-supplied input escaping. Input validation can be used to detect unauthorized input before it is passed to the SQL query. The labs in this module give hands-on experience in testing a web application against various SQL injection attacks.

Objective: Perform SQL injection attacks and other tasks that include, but are not limited to: understanding when and how web applications connect to a database server in order to access data; performing a SQL injection attack on an MSSQL database; extracting basic SQL injection flaws and vulnerabilities; detecting SQL injection vulnerabilities.

Overview of SQL Injection: SQL injection attacks can be performed using various techniques to view, manipulate, insert, and delete data from an application's database. There are three main types of SQL injection: in-band SQL injection (an attacker uses the same communication channel to perform the attack and retrieve the results), blind/inferential SQL injection (an attacker has no error messages from the system to work with, but sends a malicious SQL query to the database), and out-of-band SQL injection (an attacker uses different communication channels such as database email functionality, or file writing and loading functions to perform the attack and obtain the results).

Exam Essentials: SQL Injection

Scenario & Objective

Scenario: SQL injection is the most common and devastating attack used to take control of data-driven web applications and websites. It is a code injection technique exploiting a security vulnerability in an application's software, using malicious SQL queries to manipulate databases. Applications use SQL statements to authenticate users, validate roles, store/obtain information, and link data sources. SQL injection works when applications do not properly validate input before passing it to a SQL statement. Targeted organizations can incur huge losses in money, reputation, data, and functionality. As a pen tester you must know SQL injection techniques and protect against them using prepared statements with bind parameters, whitelist input validation, and user-supplied input escaping.

Objective: Understand when and how web applications connect to a database server to access data; perform a SQL injection attack on an MSSQL database; extract SQL injection flaws and vulnerabilities; detect SQL injection vulnerabilities.

Overview of SQL Injection

SQL injection can be used to implement: authentication bypass (log on without valid credentials, gain admin privileges), authorization bypass (alter authorization info in the DB), information disclosure (obtain sensitive stored data), compromised data integrity (deface pages, insert malicious content, alter DB contents), compromised availability of data (delete specific info, logs, audit trails), and remote code execution (execute code remotely, compromise the host OS). There are three main types: in-band (same channel for attack and results), blind/inferential (no error messages; send malicious query and infer from true/false or timing), and out-of-band (different channels such as DB email, file read/write).

Key Concepts
  • SQL Injection: Code injection exploiting unsanitized user input in SQL statements; manipulates database queries to view, insert, update, or delete data.
  • In-band SQLi: Attacker uses the same communication channel to perform the attack and retrieve results. Includes error-based and union-based.
  • Error-based SQLi: Database error messages reveal structure, table names, or data; attacker forces errors to extract information.
  • Union-based SQLi: Uses UNION SELECT to append attacker-controlled results to the original query output.
  • Blind / Inferential SQLi: No visible output or errors; attacker poses true/false questions to the DB. Subtypes: boolean-based (page content differs) and time-based (response delays via WAITFOR DELAY / SLEEP).
  • Out-of-band SQLi: Uses different channels (DNS, HTTP, email, file system) to exfiltrate data when in-band is not possible.
  • Tautology: An always-true condition such as blah' or 1=1 -- used to bypass authentication.
  • Piggybacking (stacked queries): Appending additional SQL statements separated by ; (INSERT, CREATE, DROP, EXEC) to the original query.
  • Stored Procedures: Database routines that can be abused, e.g. xp_cmdshell to execute OS commands on MSSQL.
  • Comment syntax: -- comments out the remainder of the SQL query, neutralizing trailing conditions.
  • sqlmap: Open-source automated tool for detecting/exploiting SQLi; supports boolean-based blind, time-based blind, error-based, UNION, stacked, and out-of-band techniques. Switches: --dbs, -D db --tables, -D db -T table --dump, --os-shell.
  • DSSS (Damn Small SQLi Scanner): Fully functional SQLi scanner supporting GET and POST parameters; detects blind SQLi and prints vulnerable links.
  • OWASP ZAP: Integrated pen-testing tool; Automated Scan; Alerts tab shows vulnerabilities with Risk/Confidence/Parameter/Attack; risk flags by color.
  • Burp Suite: Proxy/interceptor used to tamper with parameters and test SQLi manually.
  • MSSQL targets: GoodShopping (login table smith/smith123), MovieScope (User_Login table with plaintext passwords).
  • Cookie-based scanning: Authenticated sqlmap/DSSS scans require the session cookie from the logged-in browser.

Defenses
  • Use parameterized queries / prepared statements with bind parameters instead of string concatenation.
  • Whitelist input validation and strong typing; reject unexpected characters.
  • Escape user-supplied input where dynamic SQL is unavoidable.
  • Apply least privilege to DB accounts; disable xp_cmdshell and dangerous stored procedures.
  • Suppress verbose database errors; return generic messages to users.
  • Deploy WAF/IDS/IPS and monitor for SQLi patterns.
  • Avoid dynamic SQL in stored procedures; use parameterized calls.
Exam Tips
  • Tautology payload blah' or 1=1 -- bypasses login when input is not validated.
  • Piggybacking uses ; to stack extra statements (INSERT/CREATE/DROP/EXEC).
  • -- comments out the rest of the query, neutralizing trailing WHERE/AND conditions.
  • xp_cmdshell lets SQLi execute OS commands on MSSQL (ping, tasklist, net user).
  • sqlmap: --dbs lists DBs, -D db --tables lists tables, -D db -T table --dump dumps rows, --os-shell gives interactive OS shell.
  • DSSS detects blind SQLi and prints a vulnerable link that, when opened, reveals user accounts.
  • OWASP ZAP: Alerts tab; expand SQL Injection node; view Risk, Confidence, Parameter, Attack; risk flags Red=High, Orange=Medium, Yellow=Low, Blue=Info.
  • Blind SQLi relies on true/false questions and can be time-intensive.
  • Out-of-band SQLi uses different channels (DNS/HTTP/email/file) to exfiltrate data.
  • Authenticated scans (sqlmap/DSSS) need the session cookie copied from browser DevTools Console (document.cookie).
  • Extracted passwords may be stored in plaintext (MovieScope User_Login).
  • After injection, verify results in SSMS (Select Top 1000 Rows) or by logging in with extracted creds.

Notes: Versions/website appearance may differ; process same. Always obtain proper authorization; use these techniques only in authorized labs/environments.
